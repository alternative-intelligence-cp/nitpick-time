## Why a subcycle of its own, and why here

**Decided at planning: item 13 is `0.1.0c`, after the adoption and before
0.1.1 — not folded into 0.1.0b.**

- **The adoption is mechanical and this is design.** 0.1.0b's acceptance is
  "compiles at the new pin and nothing else changed"; a verifier can check it
  by construction. This subcycle changes what a CONSUMER may write (four fields
  refuse a write, one refuses a read), adds an arm every `Vec`/`Bytes` consumer
  owes, and narrows a specification rule (C-8b). Mixed into one commit, a
  reviewer cannot tell a clause from a contract change, and a revert of one
  reverts both.
- **Before 0.1.1, because 0.1.1 is written against it.** With the seal,
  `date_to_days`'s argument can only have come from `civil_date` (or from
  `wild` storage, the author's opt-out); 0.1.1's plan leans on that and says so.
- *Declined — item 13 inside 0.1.0b:* the orchestrator's brief allowed either;
  the two reasons above decided it.
- *Declined — the `CivilDate` seal deferred to 0.1.1:* 0.1.1 is the algorithms;
  a public-surface change there would be the one line of that diff nobody
  reviews as a surface change.

**The `CivilDate`/`CivilTime` half is the planner's addition to item 13, and it
is flagged as such.** It is not on the board's list. It is here because C-8b's
premise — *"the language has no private field"* — is **false at `c3bdae2`**
(D-313, D-314), and `tests/probe/probe15_civil_literal_bypass.npk` was written to
announce exactly this day: *"If a future compiler grows per-field visibility …
this file stops compiling — and that is the notification that C-8b can be
narrowed and `check_civil_literal` can be retired."* It stops compiling here.

## 1. What was measured — the facts this plan rests on

**The four declarations, exactly as they compile at `c3bdae2`:**

```nitpick
pub struct:Vec<T> = { hidden wild T->:items; sealed limit<ListLen> int64:count; sealed limit<ListLen> int64:cap; };
pub struct:Bytes = { sealed buffer:body; sealed limit<ListLen> int64:len; };
pub struct:CivilDate = { sealed int32:year; sealed uint8:month; sealed uint8:day; };
pub struct:CivilTime = { sealed uint8:hour; sealed uint8:minute; sealed uint8:second; sealed uint32:nanos; };
```

- **THE ORDER IS `sealed limit<R> T:f`, AND THE COMPILER'S OWN REFERENCE SHOWS
  THE OTHER ONE.** `limit<ListLen> sealed int64:count` is `NITPICK-PARSE-001`,
  *"expected a type"*, at the column of `sealed` — measured. Yet
  `TYPE_REFERENCE.md` §9.1.2's example at `c3bdae2` is
  `limit<r_level> sealed int64:n;`. `VERIFICATION_REFERENCE.md` §2.1 writes
  `sealed limit<Len> int64:count;`, and that is the order that parses. **A
  finding for the compiler side, relayed by the orchestrator, not a defect this
  subcycle stops for.**
- **`ListLen` resolves with no import** (the prelude's `pub Rules<int64>`,
  D-308 §6; its `pub` is stored since DEF-93). Its rule
  `{ $ >= 0i64, $ <= 140737488355328i64 }` admits the vacant value 0, so
  `TYPE-077` is satisfied; `Vec<T>`'s fields are `int64`, not `T`, so the
  generic struct is no obstacle to `TYPE-059`.
- **No field this plan limits has its address taken anywhere in the tree**
  (`TYPE-063` would refuse it): every `Vec`/`Bytes` function takes the struct
  through a pointer and writes the field through it, which is a write point,
  not an address.

**What a CONSUMER can and cannot do afterwards — each a program run at
`c3bdae2`:**

```
v.count = 3i64;                      NITPICK-TYPE-079   (sealed: written only inside `vec`)
int64:x = v.items[0i64];             NITPICK-TYPE-080   (hidden: not even read outside `vec`)
b.len = 2i64;                        NITPICK-TYPE-079
CivilDate{ year: 32000i32, … }       NITPICK-TYPE-079 ×3, one per field named
a.month = 13u8;                      NITPICK-TYPE-079
CivilDate:v;  then v.month           NITPICK-ASSIGN-001 -- no default value to read (D-010)
v.count, v.cap, b.len, b.body.cap,   compile and run -- a sealed field is READ anywhere
d.month, d.clone(), d.cmp(e)
```

**So C-8's guarantee is the TYPE's again, for every module but `cal`**: a
consumer cannot build, overwrite or default-read an unreal `CivilDate`. The one
route left is `wild` storage reinterpreted by `=>!` — the language's opt-out for
every checked property, and stated as such, not hidden.

**The blast radius — measured, and small:**

- **`LimitViolated` is demanded by nine roots**, every one a consumer of
  `vec.npk` or `bytes.npk`: `tests/conformance/import.npk`,
  `tests/probe/defect/generic_owning_copy/case5_vec_at_destructive.npk`,
  `tests/unit/bytes_growth.npk`, `bytes_put_int.npk`, `bytes_view_lifetime.npk`,
  `vec_at_past_end.npk`, `vec_boundaries.npk`, `vec_pop_empty.npk`,
  `vec_set_past_end.npk`.
- **`probe15_civil_literal_bypass.npk` is refused `NITPICK-TYPE-079` ×3**, as
  its header predicted.
- **Nothing else moves.** No test writes `count`, `cap` or `len` from outside,
  none reads `.items` of the library's `Vec` (the probes that index `.items`
  declare their own `Vec`), and `civil_order.npk` and `civil_construct.npk`
  build through the constructors.

**The arm bills** (a program importing the one module, no `failsafe`, reading
`NITPICK-REACH-003`'s list): `vec.npk` 8 → **9**, `bytes.npk` 11 → **12**, the
umbrella `src/lib.npk` 12 → **13**; `cal.npk` stays **11** — sealing adds no
identity.

## 3. What will bite

- **The qualifier order** (§1). If `PARSE-001 expected a type` appears at a
  field, the `limit<…>` is in front of `sealed`.
- **`body`, not `buf`.** The board's item 13 was written from the sibling
  library's field names.
- **`hidden` refuses a struct literal naming the field outside the module** —
  `Vec{ items: … }` exists only in `vec_init`, inside `vec`, so nothing here
  trips it; a test that builds a `Vec` by literal would.
- **A limited field has no address** (`TYPE-063`). `@v.count` anywhere,
  including a `$$m` claim or a pointer-receiver call on the field, refuses.
- **The seal changes nothing at run time for correct code**, and the
  `LimitViolated` check can never fire from outside the module (nothing
  outside can write the field). Do not write a test that tries to make it fire
  from a consumer; it cannot, and that is the point.

## 5. Decisions drafted at planning

Recorded by the worker in `../../DECISIONS.md` as the next free TM numbers,
in this order, in the commit that makes the change.

**PD-8 — `Vec<T>` and `Bytes` carry the three properties.** `items` hidden;
`count` and `cap` sealed under the prelude's `ListLen`; `Bytes`' `body` sealed
and `len` sealed under `ListLen` (D-308, D-313, D-314; the board's worklist
item 13, decided on safety by the compiler seat with the author). Every
`Vec`/`Bytes` consumer owes `LimitViolated` (the umbrella 12 → 13, measured).
*Alternatives:* a `VecLen` rule of our own — declined: the prelude's `ListLen`
is the bound the compiler's own length facts use, and a second copy is a second
place to disagree; `$ > 0` — declined: `TYPE-077`, a rule must admit the vacant
value 0; `count`/`cap` hidden — declined: they are read across modules and by
tests; `items` merely sealed — declined: a read of the bare pointer outside
`vec` IS the unchecked index TM-108 closed by convention, and `hidden` makes it
a compile error.

**PD-9 — `CivilDate` and `CivilTime` seal every field; `CALENDAR.md` gains C-8c.**
Supersedes TM-148 in part: its measurement (a consumer's literal compiled at
`aaffb87`) stays true of that pin; its premise (*"the language has no private
field"*) is false at `c3bdae2`. *Alternatives:* `hidden` — declined: the fields
are read everywhere, and `civil_order.npk` reads every one; not sealing and
keeping C-8b — declined: it leaves unenforced a guarantee the language can now
enforce, which is the house-rule-over-compiler shape this ecosystem refuses;
a `limit` on `month`/`day` — declined: `TYPE-077` requires the rule to admit 0,
so `$ >= 1` cannot be written, and a rule that half-states C-4 is P-7's warning.
