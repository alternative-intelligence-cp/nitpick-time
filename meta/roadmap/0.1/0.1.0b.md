## Why `0.1.0b`, decided at planning

**The adoption is its own subcycle, numbered `0.1.0b`: inserted after 0.1.0,
before 0.1.1, moving no existing number.**

- **The letter is the compiler's own convention for an inserted subcycle** —
  its 1.5.1b sat between 1.5.1 and 1.5.2, and 1.5.8b, c and d followed 1.5.8 —
  so a reader of both repositories reads one scheme. It sorts between `0.1.0`

  algorithms" and "0.1.2, the sweep — the gate" on the board, in `RECORD.md`,

  `ROADMAP.md`'s numbering rule refuses exactly that.
- *Declined — `0.1.1a`:* sorts after `0.1.1` and reads as part of the
  algorithms.
- *Declined — folding the adoption into 0.1.1:* the board's question 6 answered
  that the CI pin bump is its own commit **before any 0.1.1 work**, and a
  90-file mechanical adoption inside an algorithms subcycle can be reviewed as
  neither.

- **The rule is that CI never runs adopted code at the old pin.** The new
  clauses and arms do not resolve at `aaffb87`: `decreases` is not a keyword
  there and `StackExhausted` does not exist (the board's canary, amended with
  the two arms, is `RESOLVE-002` at `3d15ac9`). Putting the bump **first** makes
  it impossible for any commit in this repository's history to pair adopted
  code with the old pin — the property holds by construction, not by push
  discipline.
- *Declined — adoption first, bump second:* commit 1's tree would pair adopted
  code with `aaffb87`, and only the push discipline would keep CI off it.
- *Declined — one commit for both:* question 6's answer is "its own commit", and
  a pin change inside a 90-file diff is the one line a reviewer misses.
- **Commit 1 alone is RED on purpose**, and that red is information: it is this
  subcycle's "before". It is never pushed alone, and **pushing commits 0, 1 and
  2 in one `git push` makes GitHub run the workflow once, for the pushed head**
  — commit 2. (A push event runs a workflow for its head commit; the commits
  inside it get no run of their own.)
- **Commit 0 comes first because nothing else can be committed before it.**

  unchanged tree, every one a `[leak]`** — absolute home-directory paths in six

  until they are gone. Step 0b removes them, forward, in the tree — never by

- **Commit 3 exists because a CI result cannot live inside the commit that
  caused it** — `done/0.0/0.0.6.md`'s close is three commits for exactly this
  reason.
- **Expect commit 2's run to be slow and do not read slowness as trouble.** The
  workflow caches the built compiler by commit, so `c3bdae2` is a deliberate

### Step 2 — `vec_reserve<T>` relocates with `ralloc` (draft PD-2, D-264)

Replace `vec_reserve<T>`'s body from `wild int8->:mem = alloc(…)` through
`v.cap = n;` with:

```nitpick
    wild int8->:mem = ralloc(v.items =>! wild int8->, n * #size_of<T>());
    v.items = mem =>! wild T->;
    v.cap = n;
    pass NIL;
```

keeping the early return and the `n` computation above it exactly as they are.
**Rewrite the function's comment** — the paragraph beginning *"COPYING IS A
COPY AND NOT A MOVE"* is about a loop that no longer exists: the relocation is
now a BITWISE move of the whole block, correct at any `T`, and there is no
element copy for D-264 to refuse. Say that `ralloc(p, 0)` cannot happen here
(`n >= want >= 1` whenever the early return did not fire) and that a push after
`vec_free` still traps `Unreachable`, exit 95 — now in `ralloc` rather than in
`dalloc` (measured in scratch: `ralloc` of the freed block traps 95).

In the same file, the header's item 2 (*"AND THE WORSE ONE: `NITPICK-TYPE-046`
IS NOT ENFORCED INSIDE A GENERIC BODY"*) and `vec_pop`'s *"does not fire inside
a generic body"* are false at `c3bdae2`: say what D-264 now does, at which pin
it was measured, and that `vec_pop`'s `move` is still the correct spelling. The
restriction to a non-owning `T` (TM-132) **stands**, and now on one reason:
`vec_set`, `vec_pop`, `vec_truncate`, `vec_clear` and `vec_free` still owe an
element drop at an owning `T` that none of them performs.

## 8. Decisions drafted at planning

Each is recorded by the worker in `../../DECISIONS.md` as the next free TM

it describes. The text below is the draft; the worker may tighten it but not

**PD-1 — `uint64`'s maximum is `~0u64`.** D-311; at `c3bdae2`, D-310's
`NITPICK-TYPE-076` refuses `0u64 - 1u64` **even as a `fixed` initialiser**. This
replaces part of TM-134: its lesson (a constant, never a body statement)
stands, its spelling does not, and its heading gets the marker line. *Alternatives:*
`(1u64 << 63u64) | ((1u64 << 63u64) - 1u64)` — D-311 admits it; declined as a
longer spelling of the same value; `0u64 -% 1u64` — declined: a wrapping
operator where nothing wraps by design hides what the constant is.

**PD-2 — `vec_reserve<T>` relocates with `ralloc`, and TM-132's restriction now
stands on the element drops alone.** D-264 refuses `into[i] = from[i]` at a type
parameter. A relocation is a bitwise move of the whole block and `ralloc` is
that operation, correct at any `T`. Supersedes TM-136 in part: its reason 2
(*"`NITPICK-TYPE-046` does not fire inside a generic body"*) is false at
`c3bdae2`; its reason 1 and the five undischarged element drops remain, so
`Vec<T>` stays for a non-owning `T`. *Alternatives, measured:*
`move(from[i])` over the hoisted slices — `NITPICK-MOVE-001`; the slices re-made
per iteration — compiles, and spends a loop, a measure and an arm on a
bitwise copy; a byte-wise copy over `uint8` slices — re-implements `ralloc`.
*Consequence, measured:* `vec.npk`'s own bill at `c3bdae2` is 8 identities, and
a push after `vec_free` still traps `Unreachable` (95).

**PD-3 — every loop states the measure a reader can defend, and the reading is
a committed record.** `meta/roadmap/0.1/decreases_read.txt`: 29 in the tool's
shape, 19 read, none `unbounded`. In `src/`, a bound read through a pointer is
hoisted into a local so its `terminate` rows can discharge; `bytes_put_int`'s
negative loop is `decreases 0i128 - (x => int128)` because `0i64 - x`
overflows at `int64` MIN. *Alternatives:* `decreases b.len - i` for the pointer
bound — declined: `open` under DEF-14 whatever the proof effort; for the digit
loop `NTIME_DIGITS_MAX - n` — declined: a trip budget, which D-304 refuses as a
measure because it is not why the loop ends; `(0i64 -% x) =>! uint64` —
