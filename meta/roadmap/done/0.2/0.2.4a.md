`check_int128_sites` red.

### 1.5 The narrowings and the wrapping operators

## 4. The code

The two patches are the text; this section says what the harness's code does and
may not do, so a reader of a patch knows what to hold it to.

- **`check_constants_named`** reads `src/core/limits.npk` through the reader every
  check uses (`lexical.read`, `blank_code`), never imports it, and evaluates an
  initializer only if it is integer literals joined by `+`, `-`, `*` and
  parentheses — `ast`-parsed after each literal is replaced by its value, every
  node checked against that list before `eval` sees it. A tree without the file
  has no bound values, so the self-check's mini-trees plant one where they need
  one. `OWNER_PLACE` names a file or a directory; a number whose owner has none
  would be a `KeyError`, which the four owned numbers and two owners cannot reach.
- **`_view_in`** strips one `?` and recurses, before the slice test; the depth
  guard (`seen`) is the struct walk's, unchanged.
- **`_INT128`** matches the sixteen names as whole tokens over blanked code; the
  rest of `check_int128_sites` is unchanged but its messages and its headline's
  word, "`int128` or wider".
- **Every message the three checks print says what went wrong, where, and what to
  try** — §9 lists the new and changed ones for the author.
- No `.npk` file changes but three comment headers — `limits.npk`'s,
  `core.npk`'s and `limits_named.npk`'s; no tag moves; the self-check's
  count is printed by the run, derived from `selfcheck.TREE_PLANTS`.

## 9. The error sentences this subcycle adds or changes, for the author

Each is a finding a check prints; each says what went wrong, where — the file
and line, or the file and the bound — and what to try. `%s` and `%d` are the
file, line, value, spelling and name the check fills in.

**`check_constants_named` — new: a bound's value spelled outside its file.**

```text
%s:%d spells %d%s, the value of the bound <the names> that `%s` declares
(TESTING.md §2: no bound outside it). Import <the names> and read it by
name: a bound written inline is one nobody can review against the rule that
set it, and the next change to the range misses it.
```

where *the names* is the bound's, in backticks, or both bounds' joined by
*"or"* where two share the number, negated — `` `NTIME_YEAR_MIN` or
`NTIME_YEAR_MAX` `` for a 9999, since a literal does not say which it meant.

**— new: a bound whose initializer the check cannot evaluate.** Its where is
the file and the bound's name:

```text
%s declares the bound `%s` with an initializer this check cannot evaluate,
so its value cannot be held to the file (TESTING.md §2). Write it as integer
literals joined by `+`, `-`, `*` and parentheses, as `NTIME_DURATION_NS_MIN`
is: a bound the check cannot read is a bound it cannot clear.
```

**— changed: an owned number outside its owner's place.** It named the module
and one remedy, *"Give it a name in `%s` and import the name"*; it names the
place now, and the remedy that fits the case:

```text
%s:%d spells the magic number %d%s, which belongs to module `%s` and is
spelled in `%s` alone (SAFETY.md S-16, CALENDAR.md §4). <the remedy>: a
second literal copy is how two modules come to disagree about a constant
neither of them owns.
```

where *the remedy* is, for a `core` number `limits.npk` names, *"Import
`<NAME>` from `src/core/limits.npk` and read it by name"*; for one it does not,
*"Name it in `src/core/limits.npk` and import the name"*; and for a `cal`
number, *"Do the arithmetic in `src/cal/` and call it there, or move the
number's owner to `src/core/limits.npk` by a decision, as 86 400's moved
(TM-223), and read it by name"*.

**`check_no_view_returns` — a new reason in its one sentence**, otherwise
unchanged: `an optional of a view (<the wrapped type's reason>)`.

```text
%s:%d `%s` returns `%s` -- an optional of a view (`uint8[]` is a slice). No
function in `src/` returns a view (SAFETY.md S-22): a parser takes a
`uint8[]` and returns a value and an offset. A view out of its owner's frame
is what O-N9 measured reading freed memory at exit 0. If this one must, it is
a decision that loosens S-22 and names the function there.
```

**`check_int128_sites` — changed, all three**: each names the type it found,
where each said `int128`, and the first and the third now say what to try,
where neither did.

```text
%s:%d spells `%s` outside every function. A site is a function §5's table
marks (SPAN_MODEL.md N-20), and a module-level wide value is a wide value
nobody's obligation names: move it into the function that needs it, and mark
that function's row.

%s:%d spells `%s` in `%s`, and §5's table marks no `int128` site there
(SPAN_MODEL.md N-20). A wide type used where nobody reasoned about it is the
thing N-20 forbids: compute in `int64` with its own range check, or mark the
row -- with its answer -- in the same commit.

§5's table marks `%s` an `int128` site (%s:%d), and src/'s `%s` spells no
`int128` or wider type: a mark that outlived its reason (V-1c, TM-137). Mark
the row no, or put back the arithmetic it was marked for.
```

The headlines change with them — `check_constants_named`'s counts the bound
values held and names the small ones left to review, and `check_int128_sites`'
says *"`int128` or wider"* — each a count, not a sentence a reader acts on.
