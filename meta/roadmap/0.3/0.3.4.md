## 3. The steps, and what each commit carries

**Six commits, each pushed as it is made** — GitHub runs a push's head commit only, so a commit pushed beneath another
has no CI run of its own (the workbench `PLAYBOOK.md` §7). Steps 1, 2, 4 and 5 apply a patch, which `apply.py`
STAGES; step 3 is `archive.py move`, and step 4's mentions `archive.py mentions`, **each staging exactly what it
writes** — so every commit is `git commit` with no `git add`, the staged files and nothing else, with the dispatch's
`ATTRIBUTION` lines and the subject the step names; step 5 adds the worker's own files by name (5c). **This file's
title is set `RUNNING (since <date>, <stream>)` after block 0a**, in the working tree, unstaged — the move carries
it to `done/0.3/0.3.4.md` and it stays unstaged — and lands with the record. Every commit: `check_refs` clean (each
block runs it once its change is staged), and `git status --short` read.

**The order is load-bearing.** The bytecode first, so every full run after it leaves none; the findings before the
move, so each is fixed where it stands and the README's tick in the live folder; the move alone, so git follows every
file at its default threshold; the texts after the mentions, which their contexts read; 0.4.0.md once its README
says what it is handed; the gate over the closing tree.
