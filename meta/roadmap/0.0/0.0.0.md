# 0.0.0 — the language probes — RUNNING (since 2026-09-04, s2)

> **Scope:** eleven small Nitpick programs that ask the compiler whether the
> shapes `meta/specs/` depends on are spellable, compilable and correct. No
> library code is written in this subcycle. What it produces is **a verdict per
> probe** and, where a verdict is negative, an amended specification and a
> recorded decision.
>
> **Why first.** `meta/specs/` was written against the compiler's
> documentation, and the compiler project's most expensive finding is that *a
> construct that parses is not a construct that works* — most of its cycle 0.4
> was repair, and every repair dated to the cycle that had parsed the
> construct. Two of this library's load-bearing facts (a derived `Ord`
> following declaration order, and signed division truncating toward zero) are
> facts about the *compiler* that `ntime` would otherwise discover by getting
> a wrong answer for the year −1.

---

## 1. Where you are

- Nothing is built. `src/` holds placeholder directories.
- The compiler is at `../../nitpick`, cycle 1.5 (verification), self-hosting
  declared under D-202. **Do not build it from here and do not read its `build/`**: the
  artifact these probes use is the pinned toolchain the board names
  (`../BOARD.md`, W-18) — `$NPKC` and `$NPKRT`, supplied by the orchestrator or
  set by hand from `../.internal/toolchain/<commit>/`.
- There is no `ntime` harness yet. **Probes are run by hand**, one command
  each, and that is deliberate: the harness is 0.0.2 and building it against an
  unverified set of language assumptions is the mistake this subcycle exists to
  avoid.
- The probes live in `tests/probe/` and **stay in the tree permanently**. They
  are a regression suite for the language facts this library depends on, and
  0.0.2 picks them up as ordinary `program`-stage entries.

---

## 2. The command

For each probe, from the `ntime` tree root, with `$NPKC` and `$NPKRT` from the pinned
toolchain (the board names the commit, W-18):

```
$NPKC tests/probe/probeNN_name.npk -o /tmp/p.ll \
  && llc -O0 -filetype=obj -relocation-model=static /tmp/p.ll -o /tmp/p.o \
  && ld.lld -static /tmp/p.o $NPKRT -o /tmp/p \
  && /tmp/p ; echo "exit $?"
```

A probe **expected to be refused** stops at the first command, and its verdict
is the diagnostic code and span, recorded verbatim.

**Every probe exits 0 on success and a distinct positive code per assertion it
fails**, in the compiler's house style, so a failure names itself. `exit 0`
additionally asserts, through D-151, that **no `wild` allocation is live** —
which is all D-151 watches. A **managed** body is outside it, so a probe over an
owning container asserts its memory as well (§6, and TM-106).

## 3. Decisions taken at planning

- **P-0 — a probe's filename may not begin with a digit**, so probes are named
  `probeNN_topic.npk` and the `mod:` line matches. A file's module name must
  equal its basename, and no identifier may begin with a decimal digit — D-147
  gives that opening to numeric literals alone, so `mod:01_argv;` is refused
  `NITPICK-LEX-003` with `NITPICK-RESOLVE-005` behind it. *Measured the hard
  way in `nitpick-posix`'s probe 02, 2026-09-03, after every plan in the
  ecosystem had written `01_name.npk`.*
- **P-1 — a probe is a program, never a library file.** It has its own `main`
  and `failsafe` and imports nothing from `src/`.
- **P-2 — a refused probe is a *result*, not a failure of the subcycle.** One
  (11's negative twin) is expected to be refused, and its value is the exact
  diagnostic. The subcycle fails only if a verdict is *undecided* — a compiler
  crash, a hang, or output nobody can read.
- **P-3 — the verdict is recorded before the next probe is written.** A batch
  written and then run together is a batch where the third one's answer would
  have changed the fourth one's design.
- **P-4 — a negative verdict amends `meta/specs/` in the same commit.** Not a
  note to self. The specification is the authority (TM-002), and an authority
  known to be wrong and not corrected is worse than none.
- **P-5 — the probes stay.** They become `tests/probe/`'s permanent suite, so a
  compiler change that breaks one of these facts is caught by `ntime`'s own
  harness rather than by a wrong date in cycle 0.6.
- **P-6 — probes that pin a *fact about the compiler* assert the expected
  answer**, rather than printing what they found. 01 and 07 are of that kind:
  the specification already states what the answer is, so the probe's job is to
  make a change to that answer a red run.

## 4. The probes

Each entry: **what it asks**, **why it matters**, and **what a negative verdict
costs**.

### 01 — a derived `Ord` follows declaration order

**Asks:** does `#[derive(Ord, Eq)]` on `{ int64:a; uint32:b; }` compare `a`
first and `b` second?

```nitpick
#[derive(Ord, Eq)]
struct:Pair = { int64:a; uint32:b; };
// assert: Pair{a:1, b:0}  <  Pair{a:1, b:9}
// assert: Pair{a:2, b:0}  >  Pair{a:1, b:9}     // a dominates
```

**Matters because** `Timestamp` is `{ int64:secs; uint32:nanos }` and TM-011
makes the field order *semantic* on exactly this basis. Every comparison of
two instants in the library rests on it.

**A negative verdict costs** the derived comparison: `Timestamp` grows a
hand-written `timestamp_cmp`, `TIME_MODEL.md` M-6 is rewritten, and every
other value type in the library is re-examined for the same assumption.

### 02 — `int128` arithmetic and a narrowing `=>!`

**Asks:** `int128` add and compare; `=>!` down to `int64` for a value that
fits; and the **trap** for one that does not.

**Matters because** `SPAN_MODEL.md` §5 names exactly three `int128` sites and
`VERIFICATION.md` P-5 calls the narrowing there "the single most valuable proof
in the library". If the narrowing silently truncates rather than trapping, the
proof is load-bearing rather than a belt, and the code must check explicitly
before every one.

**Also measures** whether `int128` division is needed anywhere — it is not, in
the current design, and the probe records that it was checked.

### 03 — a `timespec` in a `buffer`, through `sys`

**Asks:** `buffer_new(16)`, `#ptr_add<int64>` writes and reads,
`clock_gettime(CLOCK_REALTIME=0)` as `sys(228, 0, ptr)`, both fields read back
and sane; `#size_of` and the offsets asserted.

**Matters because** every function in `src/host/` is this shape
(`HOST.md` §2), and the 16-byte two-`int64` layout is the one fact about the
kernel this library assumes.

**A negative verdict costs** `src/host/`'s implementation strategy, and
`HOST.md` §2 is rewritten against whatever does work.

### 04 — a large `fixed` module-state table

**Asks:** a module-level `pub fixed` array of ~30 000 small structs. Does it
compile? Is it emitted as read-only data? Does the program's startup do any
work for it? Is `#size_of` of the row what the arithmetic assumed?

Read the emitted IR, not just the exit code: the question is whether the array
is a `@global constant` or something a startup routine fills in.

**Matters because** the compiled tzdb (TM-007) is exactly this, at roughly
27 000 transition rows, and `ZONE_MODEL.md` §3's whole cost model assumes it is
static data with no startup cost.

**A negative verdict is the most expensive one in the set.** If a large `fixed`
table is initialised at run time, TM-007's representation changes — the
fallback would be a `buffer` built from a byte blob at first use, which
reintroduces initialisation order and a mutable global, and `ZONE_MODEL.md` §3
would need rewriting before cycle 0.5. **Run this probe early**, and pair it
with 0.0.5's size spike.

### 05 — a payload enum in a `pick` and in a `Vec`

**Asks:** a tagged enum with payloads, destructured in a `pick`, stored in and
read back from a `Vec`, and `#[derive(Eq, Debug)]` on it.

**Matters because** `FmtPart`, `ValueFault`, `ZoneFault`, `ParseExpect`,
`Weekday` and `Month` are all this shape, and `Layout` stores `FmtPart` in a
`Vec`.

### 06 — a generic `Vec<T>` with `move` and a mutating receiver

**Asks:** `move T:v` into a generic container at both a scalar `T` and an
owning one; an inherent `impl:<T>:Vec<T>` with a `Vec<T>->:self` receiver that
mutates; and the free-function form beside it, so the fallback is measured in
the same probe.

**Matters because** `TM-005`'s `Vec<T>` is the library's one container.

### 07 — signed division and modulus at negative operands

**Asks, and asserts:** that `/` truncates toward zero and `%` takes the sign of
the dividend.

```nitpick
// assert: (-7i64) / 2i64  == -3i64      (truncating, not floor's -4)
// assert: (-7i64) % 2i64  == -1i64      (sign of the dividend)
// assert:   7i64  / (-2i64) == -3i64
// assert:   7i64  % (-2i64) ==  1i64
```

**Matters because** Hinnant's `days_from_civil` (TM-016) is written for C
semantics and carries the correction `(y >= 0 ? y : y - 399) / 400` for exactly
this reason. The compiler's `TYPE_REFERENCE.md` §28 says signed `/` is `sdiv`
and `%` is `srem`, which is C semantics, so **the expected verdict is that all
four assertions hold**.

**The probe exists anyway** because if this were ever otherwise the calendar
would be wrong for negative years *only*, and cycle 0.1's exhaustive sweep
would be the first thing to notice — a long way from the cause, and only if
somebody had thought to include negative years in the sweep.

### 08 — `readlink` through `sys`

**Asks:** `readlink("/etc/localtime", buf, 4096)` through `sys(89, …)`, with
the returned length as the authority and the buffer **not** NUL-terminated by
the kernel. Assert the length, assert that byte `[len]` is untouched, and
handle the not-a-symlink case (`EINVAL`).

**Matters because** `HOST.md` H-15 names four facts about this call that a
careless implementation gets wrong, and `host_system_zone`'s second discovery
step is entirely this.

**Needs a machine where `/etc/localtime` is a symlink**, which is the usual
case; where it is not, the probe asserts the `EINVAL` path instead and records
which arm it took.

### 09 — `environ()` and a `KEY=VALUE` split

**Asks:** `environ()` read, an entry located by prefix, the value taken as a
slice, and the borrow rules exercised — passed down (legal), returned
(expected refused), stored (expected refused).

**Matters because** `host_system_zone`'s first discovery step reads `$TZ`, and
because the environment block is the kernel's and never freed (the builtin's
own documentation says so), which is a lifetime a probe should confirm rather
than assume.

### 10 — `string_bytes` / `string_from_bytes` at the borrow edges

**Asks:** `string_bytes(s)` into a scanner, the slice's `.len` and `.ptr`, a
`string_from_bytes` view built in `wild` context, and the four edges the escape
analysis governs.

**Matters because** every parser in `src/fmt/` takes a `uint8[]` and every
formatter produces a `string` through `Bytes`, and D-186 made `string_slice`
an owned copy for exactly the use-after-free this probe maps.

### 11 — the `failsafe` arm contract, positive and negative

**Asks two programs:**

- one importing a module that declares a single `error:`, whose `failsafe`
  names exactly the arms REACH-002 requires — **must compile**;
- its twin, omitting one arm — **must be refused**, and the diagnostic recorded
  verbatim.

**Matters because** TM-017's whole budget rests on the claim that a missing arm
is a *compile error*, and `SAFETY.md` §2's table is a promise to consumers.
`check_failsafe_arms` (0.0.3) is built on the same mechanism, and this probe is
what proves the mechanism is real before a check is written against it.

**A negative verdict on the negative twin** — that is, if the omission
*compiles* — would mean the error budget is a convention rather than a
constraint, and `SAFETY.md` §2, `COMPAT.md` §6 and TM-013's major-version rule
all need rewriting.

## 5. The steps

Each step is one commit.

**Step 1 — the expensive two: 04, then 01.** These are the probes whose
negative verdicts change a *representation* rather than an API. 04 decides how
the zone table is spelled; 01 decides whether `Timestamp` can derive its
comparison. Run them, record verdicts, and if either is negative **stop and
re-plan** before writing another probe.

**Step 2 — the arithmetic facts: 07, 02.** These decide whether the calendar
algorithms can be used as published and whether the `int128` narrowings need a
check before them.

**Step 3 — the host shapes: 03, 08, 09.**

**Step 4 — the remainder: 05, 06, 10, 11.**

**Step 5 — the record and the amendments.** Every verdict written into §7;
every consequence written into `meta/specs/` and `meta/DECISIONS.md`;
`tests/probe/README.md` written, saying what the directory is for and that a
probe is never deleted.

## 6. What the executor should know

- **The reserved words bite immediately.** A probe about the clock wants a
  local called `buffer`; one about division wants `mod`; one about ranges wants
  `end` and `limit`. `specs/BUILD.md` §7 has the list and the substitutes.
- **`discard(x);` takes parentheses. `defer { … }` takes no trailing
  semicolon.** Declarations end `};`; control-flow blocks do not.
- **Adjacent string literals do not concatenate.**
- **A file's `mod:` name must equal its basename**, or the loader reports
  `NITPICK-RESOLVE-005` at line 1 and says nothing about the name.
- **`raw` is licensed only on a `never fails` callee** (D-163).
- **A `failsafe` must name every reachable error** (REACH-002), including the
  system ones the program's own machinery can raise. Copy the arm set from
  `../../nitpick/tests/backend/programs/proc_tool.npk` and prune.
- **Exit 0 means "no `wild` allocation is live"** (D-151) — that, and nothing
  more. Every probe exits 0 on success on purpose, and the assertion it buys is
  precisely the one `nitpick-sockets` states about its own control buffer: a
  path that *takes no `wild` bytes* **cannot trip D-151 on any exit path**.
  It is a statement about coverage, not a proof of cleanliness.
  **A managed body is outside it**, and this subcycle measured how far outside:
  probe 06's `Vec<string>` freed its block, orphaned its elements, **retained
  125 MiB over 2 000 000 elements and exited 0** (TM-106, `SAFETY.md` S-18b).
  So a probe over an owning container asserts its memory, and an exit code is
  not that assertion. Until the instrument exists the assertion is a `ulimit -v`
  cap — probe 06's own form, where the orphaning half gives `HeapOom` (exit 92)
  and the correct half exit 0. **The real gate arrives with the compiler's
  1.5.1b step 0**, `NPK_HEAP_STATS`: an allocator-level report of `allocated`,
  `peak_live` and `count` for *managed* memory, plus a `cost` harness stage.
  Run on this repository's own two container probes it reported **`peak_live`
  41 321 bytes against 400 101 320** — the pair that both exited 0. At the
  re-pin, "assert the memory" becomes a `peak_live` bound per test, and
  cycle 0.0.3 is where the stage that carries it is written.
- **`llc` and `ld.lld` must be the pinned 20.1.2.** `llvm-config --version`.
- **Read the emitted IR for probe 04.** The exit code cannot tell you whether a
  table is static data or filled at startup; `-o /tmp/p.ll` and reading it can.

#### 1. RX-111 — the bounds promise, corrected (TM-108)

`SAFETY.md` §1 carried *"Array, slice and buffer indexing is bounds-checked and
traps | D-070 | A zone-table index out of range is a crash, not a wrong
offset."* It cited the decision whose own title is **"`T[]` is a slice: bounds
live in the array type, not the pointer type"**.

**The sentence was not false, and saying so precisely is the useful part.**
Taken literally it makes a true claim about arrays and slices — two of the kinds
the emitter actually guards. What it does is invite the reader to conclude that
*indexing* is checked in this language and then to index a `Vec` on the strength
of it. "It was true and narrow, and you read it as broad" is the mistake that
will recur; "it was false" invites a reader to distrust the rest of a table that
is otherwise sound.

Read out of the emitter rather than out of a summary —
`src/backend/ir/ir_expr.npk`'s `ExprIndexExpr` place switch, whose branches are
`TY_SLICE`, `TY_POINTER`, `TY_ARRAY` and `TY_SIMD` and nothing else:

| Branch | Guard |
|---|---|
| `TY_SLICE` | `emit_bounds_guard` against the slice's runtime `len` |
| `TY_ARRAY` | `emit_bounds_guard` against the type's constant |
| `TY_SIMD` | `emit_bounds_guard` against the lane count |
| `TY_POINTER` | **none** — straight to `getelementptr` |

and `parse_type.npk`'s second header fact — *qualifiers are not part of the
type* — makes `wild T->:items` a bare pointer to the emitter. So an out-of-range
`Vec` index is **a silently wrong value**.

**Three things the old row got wrong that nobody had noticed:**

1. **`simd<T, N>` is guarded**, and the row omitted it. The sibling
   `nitpick-regex`'s own S-23 table omits it too; not edited from here.
2. **`buffer` is named by the row but reached through the pointer branch.**
   `TYPE_REFERENCE.md` §23's own example is `buf.ptr[0i64]` — *"byte reads index
   the ptr"* — and `.ptr` is a `uint8->`. **There is no slice view of a `buffer`
   to reach instead:** `buffer_bytes`, a borrow of the body, is listed under
   §23's *"deliberately NOT landed"*, to be added by decision when a consumer
   exists. This was checked because the dispatch asserted the opposite, and it
   is the one correction that *enlarges* the problem.
3. **So `Bytes` is in the blast radius beside `Vec<T>`** — B-12 makes it an
   owning byte sink over `buffer`, and **every formatter writes into one**. The
   library's two containers are both unchecked and the specification said the
   opposite of that about both.

**The zone table, which the old row's example was about, still traps** — S-19
makes the generated tables `fixed` module state, so they are `T[N]`. The example
was right by accident, and being right by accident is why the sentence lasted.

Landed as `SAFETY.md` **S-17b** with a four-row table, the `buffer` route stated
rather than dropped, and the per-library nuance: **there is no compiler-prelude
