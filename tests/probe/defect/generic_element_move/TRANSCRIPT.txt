=======================================================================
PART C -- the arm bill for both accessor spellings (TM-129's evidence)
=======================================================================

WHY THIS IS HERE. `case1` above blocks one row of `0.0.4.md` §2's table; the
rest of that table still has to be written, and the accessor is the row every
other row leans on (`SAFETY.md` S-17b: the accessor pair is the only bound
`Vec<T>` has). TM-129 settles its spelling. The one argument that could have
gone against it is cost to a consumer, and this is the measurement that
answers it: BOTH spellings bill the SAME SIX identities, so the guard is free.

The two scratch modules, quoted in full so this is reproducible. They differ in
`vec_at`'s body and nowhere else. NOT committed as probes because
`harness/arms.py`'s `check_failsafe_arms` already generates exactly this
program for every public module in `src/` on every run -- so the day
`src/core/vec.npk` lands, this measurement is re-derived and ASSERTED by the
suite rather than quoted from here.

    # t2/core/vec.npk -- the guarded spelling
    mod:vec;
    pub struct:Vec<T> = { wild T->:items; int64:count; int64:cap; };
    pub func:vec_init<T> = Vec<T>(int64:cap) never fails {
        int64:n = cap;
        if (n < 1i64) { n = 1i64; }
        wild int8->:mem = alloc(n * #size_of<T>());
        pass Vec{ items: mem =>! wild T->, count: 0i64, cap: n };
    };
    pub func:vec_at<T> = T(Vec<T>->:v, int64:i) never fails {
        T[]:s = #wild_slice<T>(v.items, v.count);      # <-- THE ONLY DIFFERENCE
        pass s[i];
    };
    pub func:vec_free<T> = NIL(Vec<T>->:v) never fails {
        dalloc(v.items =>! wild int8->);
        v.count = 0i64; v.cap = 0i64; pass NIL;
    };

    # t3/core/vec.npk -- the unguarded spelling: `vec_at`'s body is one line
    pub func:vec_at<T> = T(Vec<T>->:v, int64:i) never fails {
        pass v.items[i];                               # <-- THE ONLY DIFFERENCE
    };

    # the consumer, identical for both, DELIBERATELY WITHOUT a `failsafe`,
    # which is what makes NITPICK-REACH-003 list the bill (S-6b)
    mod:consumer;
    use "./core/vec.npk".*;
    func:main = int32(cstring[]:argv) {
        Vec<int64>:a = raw vec_init::<int64>(4i64);
        a.items[0i64] = 11i64;
        a.count = 1i64;
        if (raw vec_at(@a, 0i64) != 11i64) { exit 10i32; }
        if (argv.len > 0i64) { discard(raw vec_at(@a, 5i64)); }
        drop vec_free(@a);
        exit 0i32;
    };

THE SETS ARE EQUAL, AND THE ARITHMETIC IS WRITTEN OUT SO IT CAN BE CHECKED:

    6 = 4 (S-4b's floor: Unreachable, HeapOom, HeapBadRequest, WildLeak)
      + 1 (IntOverflow, from `n * #size_of<T>()` in `vec_init`)
      + 1 (OutOfBounds, from the index)

  and no `DivByZero`/`DivOverflow`, because `vec.npk` divides by nothing --
  which is the per-module granularity S-4c describes, and which predicts that
  `src/core/bytes.npk` will bill EIGHT, since `put_uint` divides by 10.

AND HERE IS THE PART THAT IS WORTH MORE THAN THE DECISION IT SETTLES.

**THE UNGUARDED SPELLING BILLS `OutOfBounds` TOO.** The reachability analysis
arms it for a BARE POINTER index -- for which `ExprIndexExpr` emits no
`emit_bounds_guard` at all (TM-108, S-17b) -- so every consumer of an
unguarded `Vec` is compelled to write an arm for a trap that CANNOT FIRE,
while the read it is supposed to protect returns a wrong value in silence.

That is why TM-108 went unnoticed for as long as it did: the arm bill, which is
the one artefact a library author reads when asking "what can go wrong here",
is BYTE-IDENTICAL between the safe spelling and the unsafe one. It is the same
shape as everything else in this family -- an instrument whose name says
"what can reach the handler" while its mechanism says "what the front end
thinks might". Adding the guard makes the arm honest; it does not add it.
