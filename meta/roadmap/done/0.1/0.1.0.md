## 2. The types, exactly as they will be declared

From `CALENDAR.md` §3. **Field order is comparison order** (C-6, and the
compiler's **D-123**: `Ord` compares in declaration order), so the order below
is semantic and is not to be tidied.

**COPY THESE FROM THE SPECIFICATION, VERBATIM. They are not restated here from
memory** — `CALENDAR.md` §3's code block is the authority (TM-002) and it is
narrower than a plan written from habit would be:

```nitpick
pub struct:CivilDate = { int32:year; uint8:month; uint8:day; };
pub struct:CivilTime = { uint8:hour; uint8:minute; uint8:second; uint32:nanos; };
pub struct:CivilDateTime = { CivilDate:date; CivilTime:time; };

pub enum:Weekday = { Monday; Tuesday; Wednesday; Thursday; Friday; Saturday; Sunday; };
pub enum:Month   = { January; February; March; April; May; June;
                     July; August; September; October; November; December; };
```

Note the field name is **`nanos`**, not `nano`, and enum members are separated
by `;` and not by `,`. Both are the specification's spelling.

### THE ONE THING IN THIS SUBCYCLE MOST LIKELY TO NEED A DECISION

**The fields are NARROW and there is no checked narrowing** (TM-105, S-15b).
`=>!` truncates in silence and the checked `=>` at the same narrowing is
refused outright (`NITPICK-TYPE-009`), so **every one of these fields is a
narrowing site**: `civil_date(y, m, d)` takes `int64` arguments — anything else
pushes the problem to the caller — and must range-check `y` against `int32`,
`m` and `d` against `uint8`, **in code, written by you**, before `=>!`.

That is a feature, not an obstacle: C-8 already requires the range check for
semantic reasons (`month` must be 1…12, which is narrower than `uint8`
anyway), so **the narrowing check and the validity check are the same check**
and there is no extra work. Do it in that order — validate, then narrow — and
never the reverse, because a truncated value can land back inside the valid
range and pass the check that was supposed to catch it. `m = 269` truncates to
`13` (refused, by luck); `m = 268` truncates to `12` (**accepted, and wrong**).
Write that case as a test.

**If, while writing it, the narrow fields turn out to cost more than they
save**, the answer is a numbered decision amending `CALENDAR.md` §3, **not** a
struct that disagrees with the specification. Amending is the sanctioned move
(`CLAUDE.md`) and TM-143 exists because four specifications were left standing
while the code and a roadmap file said otherwise. The recommendation, recorded
here so it is an input rather than a rediscovery: **keep the narrow fields.**
`ZONE_MODEL.md`'s tables and `SPAN_MODEL.md`'s arithmetic both assume this
layout, `#size_of<CivilDate>()` is 8 bytes rather than 24, and the one real
cost — the truncation trap above — is a test, not a design.

**`Weekday` and `Month` are payload-free enums, Monday first (C-7).**
Payload-free is deliberate and is now load-bearing: O-N10's derives are fixed
(TM-111) and a payload enum's `Ord` works, but every element-lifetime question
disappears entirely for a payload-free one. `FORMAT_MODEL.md` §3's `Layout`
vector is the only payload enum this library plans, and it is 0.4's.

### The derives, and the probe verdict each rests on

```nitpick
#[derive(Eq, Ord, Clone, Debug)]
```

- **`Ord` compares in declaration order** — probe 01 measured it, `0.0.0.md`
  §7 records the verdict, and the compiler's D-123 states it. **Cite D-123 and
  not D-051**: cycle 0.0.4 cited D-051 for four subcycles and D-051 is *"No
  `ostring`; portability lives in a `Path` type above `nlibc`"* (E2, TM-143).
- **`Eq` on a payload-free enum** — probe 05b: `#[derive(Eq)]` on a PAYLOAD
  enum was `NITPICK-TYPE-034` at the old pin and is fixed at `aaffb87`
  (TM-111). These enums have no payload, so neither the old nor the new
  behaviour is at issue; the probe is cited so a later reader does not re-run
  it.
- **A test asserts the comparison order per type** (checklist item 1), because
  a derive that compiles is not a derive that compares correctly — which is
  exactly what O-N10 was: `#[derive(Ord)]` compiled and reported `Literal(7)`
  equal to `Literal(9)`.

## 3. The constructors — the whole contract of this cycle

**C-8: validating constructors only. No unchecked constructor exists.**

```nitpick
pub func:civil_date = CivilDate(int64:y, int64:m, int64:d) fails ETimeValue { … }
pub func:civil_time = CivilTime(int64:h, int64:mi, int64:s, int64:n) fails ETimeValue { … }
```

> **CORRECTED AT EXECUTION, 2026-09-06 — `fails <Identity>` IS NOT A SIGNATURE
> CLAUSE and the two lines above do not compile.** Measured at pin `aaffb87`:
> `npkc` exits **1** with no `.ll` written, reporting `NITPICK-PARSE-001` at
> the `fails` token: *expected `;`, found `fails`*.
> The contract window after a parameter list admits `requires`, `ensures`,
> `acquires`, `never fails`, `joins` and `pure` and nothing else
> (`LEXICAL_REFERENCE.md` §4's `Contracts` production, read at the pin).
> `fails` is a `VerificationKeyword` because D-002's FFI error contracts used
> it, and D-149 removed in-process FFI. **A fallible function simply OMITS
> `never fails`** and its caller sees `Result<T>` — which is what
> `CALENDAR.md` C-8 says and what the code does:
>
> ```nitpick
> pub func:civil_date = CivilDate(int64:y, int64:m, int64:d) { … fail ETimeValue; … }
> ```
>
> Left in place rather than rewritten, because a plan is a record of what was
> planned and this is the kind of thing a later reader will otherwise copy.

Everything downstream — every conversion, every format — skips the question of
whether a date is real, **because `CivilDate` cannot hold an unreal one**. A
single unchecked constructor added for convenience removes that guarantee
everywhere at once, and it will be asked for.

> **CORRECTED AT EXECUTION, 2026-09-06 (TM-148, `CALENDAR.md` C-8b).** The
> sentence above is true of this LIBRARY and not of the TYPE. A consumer can
> write `CivilDate{ year: 32000i32, month: 99u8, day: 99u8 }` and it compiles,
> links and runs at exit 0 — measured at pin `aaffb87` — because the language
> has no private field and `opaque struct:Name = { … };` is refused. **So
> "everything downstream skips the question" is not available to 0.1.1**:
> `date_to_days` is to be written total over every field value, which
> Hinnant's algorithm already is. `check_civil_literal` keeps `src/` inside the
> guarantee; nothing can keep a consumer inside it. Left in place rather than
> rewritten, because this reading is exactly what the next reader would arrive
> at unaided.

**`civil_date` refuses**, each with its own detail field so a caller can tell
them apart without a second error identity (S-3):

| Refused | Because |
|---|---|
| `y` outside `[NTIME_YEAR_MIN, NTIME_YEAR_MAX]` | S-13, TM-014 — `−9999 … +9999` |
| `m` outside `[1, 12]` | there is no month 13 |
| `d < 1` | there is no day 0 |
| `d > days_in_month(y, m)` | February 30th, and April 31st |

**The last row depends on `days_in_month`, which is 0.1.1's.** Two options and
the decision is taken here so 0.1.1 does not re-litigate it:

> **`days_in_month` and `is_leap_year` are written in THIS subcycle**, in
> `src/cal/cal.npk`, because the validating constructor cannot exist without
> them and a constructor that validates three of its four conditions is not a
> validating constructor. 0.1.1 then owns `date_to_days`/`days_to_date` and
> the round trip. The cycle README's split is by algorithm and this is the one
> place it has to bend; it is recorded here rather than discovered there.

**`civil_time` refuses hour 24** (C-9). The normalising acceptance — `24:00:00`
as midnight of the next day — belongs to the parser at 0.4 and **is not
smuggled in here**, because a type that accepts hour 24 has two spellings of
midnight and every comparison has to know it.

**Nanoseconds** are `[0, 999 999 999]`, `NTIME_NANOS_PER_SEC − 1` from
`limits.npk` (S-12: the bound is a named constant, never a literal, and
`check_constants_named` enforces it). The field is `uint32:nanos`, so
999 999 999 fits and the check is semantic rather than a width check.

**And the year bound is `int32`-narrowing as well as semantic.**
`NTIME_YEAR_MIN`/`MAX` are ±9999, far inside `int32`, so the semantic check
subsumes the width check — but write it as the semantic check against the
NAMED bound, never as a width check, or a later widening of the range silently
becomes a truncation.

## 6. What will bite, specifically

- **Negative years.** Probe 07 pinned that `/` truncates toward zero and `%`
  takes the sign of the dividend (C semantics, `TYPE_REFERENCE.md` §28).
  Hinnant's algorithm carries the correction — `(y >= 0 ? y : y - 399) / 400` —
  and **any NEW arithmetic written here has to carry it too.** The leap rule is
  the first place it bites: `y % 4 == 0` is FALSE for `y = -4` under C
  semantics only if you get the sign wrong, and `y % 100` and `y % 400` compound
  it. **Write the leap rule against `y` made non-negative first, or write the
  correction and test year −1, −4, −100, −400 explicitly.**
- **`limit` and `end` are reserved**, and a range-bounds module wants both.
  `PLAYBOOK.md` §10 and `BUILD.md` §7 have the tables; this library uses `hi`
  and `lo`. Also reserved and easy to reach for here: `unit`, `in`, `on`,
  `mod`, `fixed`, `range`, `error`, `any`, `is`, `never`, `fails` — and
  **every field name §2 uses is clear**: `year`, `month`, `day`, `hour`,
  `minute`, `second`, `nano`, `date` and `time` were each compiled as a local
  binding at pin `aaffb87` and all nine are accepted (`npkc` exit 0). MEASURED
  at this subcycle's writing rather than read off a list, because `stack` is on
  no list in this repository and is the one that costs an hour.
- **`result` and `old` are reserved `VerificationKeyword`s** (TM-130). The
  contract comments here will want `ensures result.year == y`. Use **`answer`**
  and **`outgoing`**, which is what `src/core/` uses.
- **`stack` is a memory qualifier**, and using it as a local name gives
  `PARSE-002` at the declaration followed by *"this `{` is never closed"*
  pointing at `main`'s closing brace. A sibling library lost an hour to it.
- **A file's `mod:` name must equal its basename** and is an identifier
  (D-248), so no leading digit and no reserved word.
- **Adjacent string literals do not concatenate**; `discard(x);` takes
  parentheses; `defer { … }` takes no trailing semicolon; declarations end `};`
  and control-flow blocks do not.

#### What was found — three things, and two of them amend a specification

**1. AN `error:` IDENTITY CANNOT CARRY A PAYLOAD (TM-147, C-5b).**
`CALENDAR.md` C-5 said *"a range violation is `ETimeValue` with a
`ValueFault`"*, which is how a reader coming from an exception language writes
it and which this language cannot express. Measured:

```
$NPKC .internal/scratch/spell03.npk -o spell03.ll
  → npkc exit 1, NO .ll written
  NITPICK-PARSE-001 …:3:21: expected `;`, found `(`
```

Committed as `tests/probe/probe14_error_payload_refused.npk` so the harness
**re-derives the verdict every run** rather than a transcript recording it
once. The second half of the fact is what makes the conclusion about the
language rather than about one spelling: `Result<T>` is `{ T value, tbb32 err }`,
so the error half of every return is a **code** and there is nowhere for a
payload to live in any case. How a refusing constructor delivers the fault is
**O-X8**, deliberately open — every candidate adds a public name and TM-013
makes that a MAJOR-version commitment, so a name chosen without a caller is a
name chosen without a requirement.

**2. THE STRUCT LITERAL IS AN UNCHECKED CONSTRUCTOR (TM-148, C-8b) — and this
is the finding that matters, because C-8 is what cycle 0.1.1 was going to be
written against.** C-8 said *"There is no unchecked constructor: a `CivilDate`
that exists is a date that exists, which is what lets everything downstream
skip the question."* Measured, with every status paired to its artefact and the
whole four-step recipe run because `npkc` exit 0 is not well-formedness
(TM-112):

```
CivilDate:fake = CivilDate{ year: 32000i32, month: 99u8, day: 99u8 };
  npkc  exit 0, .ll written        llc   exit 0, .o written
  ld.lld exit 0, exe written       ./bypass  exit 0, fake.month == 99
```

And there is no mechanism to prevent it: visibility is per-declaration and
there is no per-field form, and `opaque struct:Name = { … };` is refused
`NITPICK-PARSE-001` — the bodyless form is the extern-driver declaration
(D-149) and nothing else. **This is the language as specified, not a compiler
defect**, so nothing is raised upstream and nothing is worked around.

**Extent, measured before the fix rather than after, and stated with its
denominator:** four live sites carried the strong reading, over **177 tracked
files** with the archived cycle 0.0 excluded — C-8 itself,
`meta/roadmap/0.1/README.md`, this file, and `src/cal/cal.npk`'s header as
first written. Only one of the four is a specification. Two grep phrasings were
run, case-insensitively, and the count was confirmed by reading each site
rather than by the sweep — the property is *"asserts the guarantee"*, which is
a claim about meaning and not about presence, so the sweep built the candidate
list and reading was the check.

**And the measurement is committed**, as
`tests/probe/probe15_civil_literal_bypass.npk` — `expect-exit: 0` meaning *the
bypass still works*, with its control (the same values through `civil_date`,
refused) beside it, because a file showing only the bypass half is consistent
with the constructor being broken too. It was added AFTER the first commit of
this subcycle, on noticing that the lesser of the two findings (TM-147) had a
committed probe and the greater one had four exit codes in gitignored scratch.

**The half that is fixable was fixed:** `check_civil_literal` fails the run on
a `CivilDate{` or `CivilTime{` literal in `src/` outside `src/cal/cal.npk`, and
it is **commissioned** (TM-126) — two planted violations, two clean controls,
the self-check going from 16 planted violations to 18. **One control is the
banned form in a COMMENT**, because `src/lib.npk`'s header spells the fake-date
literal out in prose to document this very rule: a grep-shaped check fails the
repository on the paragraph arguing for it, which is `check_purity`'s
first-run failure met in advance rather than discovered.

The half that is not fixable is stated plainly: the guarantee is about the
values this library **produces**. That is still a strong and useful guarantee.
It is simply not the one C-8 claimed, and 0.1.1 must write `date_to_days` to be
total over every field value rather than correct only on valid input —
Hinnant's is, by construction, so the cost is a header sentence and not an
algorithm.

**3. THE NEGATIVE-YEAR CORRECTION IS NOT NEEDED IN THE LEAP RULE, AND §6
PREDICTED IT WOULD BE.** §6 warned that `%` takes the sign of the dividend and
that "the leap rule is the first place it bites". It does not bite, and the
reason is worth recording because the warning is right in general: **every
clause of C-3 compares a remainder against ZERO, and zero has no sign.**
`-4 % 4`, `-100 % 100` and `-400 % 400` are all `0`. A correction IS still owed
by `days_from_civil`'s `era`, which uses a non-zero remainder — so 0.1.1 still
owes `(y >= 0 ? y : y - 399) / 400`. The four cases §6 names are committed as
named tests either way, because a rule that is right and a rule that is right
by accident pass the same positive-year suite.

#### The arm bill — measured, with the command, never predicted

The checklist item read *"a program importing only `cal` owes exactly one
arm"*. **It owes nine.** The command, run before any document was written:

```
$ cat .internal/scratch/arms/arm_cal.npk
  mod:arm_cal;
  use "../../../src/cal/cal.npk".*;
  func:main = int32(cstring[]:_~argv) { exit 0i32; };
$ $NPKC .internal/scratch/arms/arm_cal.npk -o arm_cal.ll
  → exit 1, no .ll written
  NITPICK-REACH-003 …:4:1: `main` without `failsafe` (D-013) … 9 identities:
    cal.ETimeValue, Unreachable, HeapOom, HeapBadRequest, WildLeak,
    DivByZero, DivOverflow, IntOverflow, OutOfBounds
```

`9 = 4 (floor) + 1 (identity) + 4 (cal's own arithmetic, charged to the
consumer)` — TM-107 exactly, and §4 predicted the falsification.
`check_failsafe_arms` reproduces it independently on every run and diffs it
against the set computed from source **in both directions**, so the number
cannot go stale. `SAFETY.md` S-4's totals column now carries it with the
command.

**AND THE ARM SET IS A SET — the first measurement here to show it.**
`tests/conformance/import.npk` went from **8** to **9**, not from 8 to 12:
`src/core/` had already armed all four system arms, and a second module doing
the same kind of arithmetic adds nothing. So S-4b's system-arm half is
**front-loaded** — it arrives with the first module that computes anything and
never grows again — while the identity half grows one per module that declares
*and raises*. That file predicted at 0.0.4 that it would be where the next move
first showed, and it was, alone in the suite again.
