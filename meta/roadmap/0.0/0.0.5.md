# 0.0.5 — the tzdb size spike — DONE (2026-09-05)

> **Scope:** run the zone-table generator's core loop far enough to emit a real
> table, compile it, and **measure it**. Nothing is committed but the number.
>
> **Why in cycle 0.0.** TM-007 — the compiled-in time-zone database — is the
> decision this library rests on, and its cost is currently an *estimate*
> derived from the system database's TZif headers (`ZONE_MODEL.md` §3: 447
> zones, 26 838 transitions, ≈348 KiB). Estimates of emitted size are wrong in
> both directions routinely. Finding at cycle 0.5 that the real answer is 4 MiB
> would reopen a decision every specification in this repository already
> depends on. An afternoon now removes that risk.

## 1. Decisions taken at planning

- **P-28 — the spike is throwaway and is *named* throwaway.** It lives in
  `meta/scratch/tzdb_spike/`, it is not `tools/gen_tzdb.py`, and 0.0.6's
  checklist deletes it. A half-finished generator left in `tools/` is a thing
  somebody later mistakes for the real one — the compiler's `bootstrap/
  generator/` carries a README saying exactly that, for exactly that reason.
- **P-29 — what is kept is the number, in three forms**: emitted `.npk` source
  bytes, emitted `.ll` bytes, and linked object bytes. The last is the one that
  matters to a consumer and the one the estimate did not predict.
- **P-30 — the spike depends on probe 04.** If a large `fixed` module-state
  table is not emitted as read-only data, the size question is the *second*
  problem and the representation is the first. Run 0.0.0's probe 04 before
  this.

## 2. Steps

1. **Read the release.** Point the spike at the pinned tzdata release's
   compiled TZif files. Parse the v2+ header, the 64-bit transition block, the
   type block, the abbreviation pool and the POSIX footer string. Python's
   `struct` is the whole of it; this is what `tools/gen_tzdb.py` will do
   properly at 0.5.
2. **Emit the four tables** in `ZONE_MODEL.md` §3's shape — transitions, types,
   the zone index, the name pool — as one `.npk` file of `pub fixed` arrays.
   Correctness is not the goal here; *shape and volume* are. Skip the POSIX
   rule parsing entirely and emit `-1` for every zone.
3. **Compile it.** `npkc` the file, `llc` it, and record all three sizes.
4. **Assert the row sizes.** `#size_of<ZoneTransition>()` and friends, so that
   §3's arithmetic is checkable rather than asserted.
5. **Read the IR.** Confirm the tables are `@global constant` data and that
   nothing initialises them at run time — probe 04's answer, at the real scale.
6. **Record.** The numbers into this file's §4 and into
   `meta/research/tzdb-size.md`, beside the estimate they test.
7. **Delete the spike**, or leave it under `meta/scratch/` where nothing
   imports it. 0.0.6 checks.

## 3. The decision this feeds

| Measured object size | What happens |
|---|---|
| ≤ ~500 KiB | as estimated. TM-007 stands, O-X2 closes, 0.5 proceeds. |
| ~500 KiB – 1 MiB | TM-007 stands. Record the number prominently in `README.md` and `COMPAT.md`, because a consumer should not be surprised by it. |
| > ~1 MiB | **stop.** Reopen O-Z1 before cycle 0.1 starts. The candidates, in order: drop pre-1900 transitions (they are LMT approximations — `ZONE_MODEL.md` Z-13); delta-encode transition times, which are monotonic and mostly a few years apart; or a build-time zone subset, which is the option the ecosystem's lack of build configuration makes worst. |

**Rule:** the third row is a *stop*, not a note. A decision the whole
specification set rests on does not get to be wrong quietly.

## 4. Measurements

**Taken 2026-09-05 at pin `aaffb87`, against tzdata 2026c.** TM-135 has the
argument; `meta/scratch/tzdb_spike/TRANSCRIPT.txt` has every command with its
exit status beside the artefact it produced.

| Quantity | Estimate (`ZONE_MODEL.md` §3) | Measured |
|---|---|---|
| canonical zones | 447 | **447** (= 446 + `Factory`, excluded by name in the first sweep) |
| transitions | 26 838 (the v1 block) | **27 183** (the v2+ block) |
| local-time types | 2 484 | **2 513** |
| largest single zone | `Europe/London`, 242 | **`Asia/Hebron`, 310** |
| `#size_of<ZoneTransition>()` | 12 | **16** |
| `#size_of<ZoneType>()` | 8 | **8** |
| `#size_of<ZoneEntry>()` | 16 | **28** |
| `#size_of<PosixRule>()` | — | **32** |
| emitted `.npk` bytes | — | **2 040 106** (2 156 824 with `POSIX_RULES`) |
| emitted `.ll` bytes | — | **1 900 429** (1 956 382) — path-dependent, see below |
| object (`.o`) bytes | — | **510 872** (525 600) |
| linked static binary | — | **543 432** (558 064) |
| **the tables themselves** | **≈356 119** | **475 006** = 463.9 KiB |
| **the same, with `POSIX_RULES`** | not estimated | **489 310** = 477.8 KiB |
| tables are `constant` | assumed | **yes, every one; `llvm.global_ctors` absent, no `= global` line at all** |
| startup cost | assumed zero | **zero** — `.data` 112 B and `.bss` 696 B in the linked binary |

**The table figure, read off the object with `nm -S` and not computed:**

| symbol | bytes | = rows × width |
|---|---|---|
| `TRANSITIONS` | 434 928 | 27 183 × 16 |
| `TYPES` | 20 104 | 2 513 × 8 |
| `ZONES` | 12 516 | 447 × 28 |
| `NAME_POOL` | 6 592 | 6 592 × 1 |
| `ABBR_POOL` | 866 | 866 × 1 |
| **total** | **475 006** | |
| `POSIX_RULES` | 14 304 | 447 × 32 |

434 928 + 20 104 + 12 516 + 6 592 + 866 = **475 006**; + 14 304 = **489 310**.

**The baseline control**, because an object size is the program's as well as
the tables': the same program at **one zone** is a 36 096 B object carrying
82 B of tables, so the program-and-prelude share is **36 014 B**, against
510 872 − 475 006 = **35 866 B** taken the other way — 148 B apart. In the
linked binary the two routes give 68 414 and 68 426, 12 B apart.

**Cost:** `npkc` 1.28–1.39 s at 28 160–28 352 KiB over three runs, `llc`
0.07–0.08 s, the object byte-identical every time. On the previous pin this
measurement would have been a different kind of afternoon; O-N4's discharge is
what made it an hour.

**One caution for a re-derivation:** the `.ll` byte count embeds
`npk.site.paths`, so emitting the same source from two directories whose names
differ by one character moved it by exactly 14 bytes — one per site — while the
object and the binary did not move at all. Quote the object.

**Instrument commissioned before any number was believed**: five zones emit,
compile and run clean, printing `swept 101` — the domain the header declares;
the same file with one transition's clock wound backwards exits **23** on Z-8's
invariant; the same file with one zone's `trans_count` understated by three
exits **24** and prints no `swept` line.

## Execution record

**Worked 2026-09-05 by stream s2 at pin `aaffb87` (the compiler's 1.5.2d
close), the first work in this repository on that pin.**

### What was done

Two things, and the second was not on the plan.

**1. The spike.** `meta/scratch/tzdb_spike/` reads tzdata 2026c's TZif files
(RFC 8536: the v1 header, the v2+ 64-bit block, the type block, the
abbreviation pool, and the footer captured but deliberately not parsed) and
emits one `.npk` of `pub fixed` tables in `ZONE_MODEL.md` Z-7's shape. Two
variants: the plan's four tables with `posix_rule: -1` everywhere, and the same
plus `POSIX_RULES` at its real cardinality with placeholder contents. The
second is not what §2 step 2 asked for and it is the number TM-007 actually
needs — the plan is right that the footer must not be *parsed* here, and
omitting the table would have left a 500 KiB budget short by 14 304 bytes with
a 22 690-byte margin. Both are reported.

§4 has the measurements. **475 006 bytes for the four tables and two pools,
489 310 with `POSIX_RULES`** — row one of §3, so TM-007 stands, O-X2 closes and
O-Z1 settles as "ship them all" (TM-135).

**2. TM-132's restriction, re-examined because O-N17 is fixed — and it stays.**
The dispatch carried this as an inherited item: verify the library's own
spelling rather than assume the compiler fix carries. It does not carry, twice
over, and the second reason is a compiler defect nobody was looking for.

### What was found

**O-N17 is fixed.** All five reproduction cases compile, assemble, link and run
at exit 0. Recorded in `tests/probe/defect/generic_element_move/TRANSCRIPT.txt`
PART D, appended and not substituted, and both `case1` and `case5` now carry
`// expect-exit: 0`.

**The library's own drop-loop spelling is refused.** One hoisted `#wild_slice`
binding with `move(s[i])` in a loop is `NITPICK-MOVE-001` — and at `T = int64`
as well, so it is a move-tracker rule about bindings and not an ownership one.
Three controls place it exactly: one move outside a loop is fine, the slice
re-made inside the loop body is fine, and `move(v.items[i])` through the bare
pointer is fine but loses TM-129's bounds guard.

**And the one that decided it: `NITPICK-TYPE-046` does not fire inside a
generic body.** `T:answer = s[i]` at an owning `T` is accepted, links, runs,
and leaves two owners of one heap body; the identical statement with `string`
written out is refused. `case4` drops the first owner and reads through the
second: exit **170**, the allocator's `0xAA` poison. Reproduced at all four
pins this workbench has used, so it is not a regression at `aaffb87` — what
changed is that O-N17's fix lets the owning instantiation reach the linker, so
the consequence became runnable. `tests/probe/defect/generic_owning_copy/`,
cited by path and deliberately unnumbered.

**The extent was measured separately from the existence, and it is two rows.**
All nine `Vec<T>` rows were instantiated at `T = string` against the real
`src/core/vec.npk`; **all nine compile, link and run at exit 0**, which is why
the exit code decided nothing. `vec_pop<T>` shipped as the bare read — the
defect's own `case1` function — and now writes the `move` that always belonged
there. `vec_at<T>` at an owning `T` **removes** the element, because `pass` of
a place moves implicitly; that one is the language behaving as specified, and
what was wrong was this repository's comment claiming TYPE-046 refused a copy
there. `vec_reserve<T>` is correct at an owning `T` **by accident** — its copy
loop leaves one owner because the old block is freed — and the file now says so.

**O-N17's two `EXPECT_EXEMPT` entries had expired and nothing noticed.** The
entry's own text promised that on the day the defect landed it would "fail the
both-directions diff"; that diff checks only that the named file still exists.
The suite was GREEN with both stale entries in place. `check_exemptions_live`
now records each exemption's verdict — `npkc`, `llc`, `ld`, `run:<code>`,
`none` — and re-derives it on every full run; commissioned green at 6 of 6, and
red with one verdict changed (TM-137).

### What it cost

The spike's inner loop is 1.3 s of `npkc` and 0.08 s of `llc` on a two-megabyte
source file, at 28 MB peak. **On the previous pin the same shape was the
measurement O-N4 blocked this subcycle over**; its discharge is what turned an
afternoon into an hour, and the 94% prelude cut at this pin is why the full
harness is 42 s rather than 241 s.

### What is deliberately not here

**A lift of TM-132.** The dispatch authorised one if the library's spelling
worked. It does not, and even the spelling that does work would rest on a rule
the compiler cannot enforce — which is what
`compiler-defects-block-not-house-rules` says to hold on. The cost of holding
is nil: `ntime` instantiates no owning `T` by design.

**A number for the real generator.** This is a spike (P-28). The four tables
are not sorted, links are not resolved, and the POSIX rows are placeholders.
None of those changes a byte count, and all of them are 0.5's.
