  that the CI pin bump is its own commit **before any 0.1.1 work**, and a

### Step 2 — `vec_reserve<T>` relocates with `ralloc` (draft PD-2, D-264)

Replace `vec_reserve<T>`'s body from `wild int8->:mem = alloc(…)` through
`v.cap = n;` with:

```nitpick
    wild int8->:mem = ralloc(v.items =>! wild int8->, n * #size_of<T>());
    v.items = mem =>! wild T->;
    v.cap = n;
    pass NIL;
```

keeping the early return and the `n` computation above it exactly as they are.
**Rewrite the function's comment** — the paragraph beginning *"COPYING IS A
COPY AND NOT A MOVE"* is about a loop that no longer exists: the relocation is
now a BITWISE move of the whole block, correct at any `T`, and there is no
element copy for D-264 to refuse. Say that `ralloc(p, 0)` cannot happen here
(`n >= want >= 1` whenever the early return did not fire) and that a push after
`vec_free` still traps `Unreachable`, exit 95 — now in `ralloc` rather than in
`dalloc` (measured in scratch: `ralloc` of the freed block traps 95).

In the same file, the header's item 2 (*"AND THE WORSE ONE: `NITPICK-TYPE-046`
IS NOT ENFORCED INSIDE A GENERIC BODY"*) and `vec_pop`'s *"does not fire inside
a generic body"* are false at `c3bdae2`: say what D-264 now does, at which pin
it was measured, and that `vec_pop`'s `move` is still the correct spelling. The
restriction to a non-owning `T` (TM-132) **stands**, and now on one reason:
`vec_set`, `vec_pop`, `vec_truncate`, `vec_clear` and `vec_free` still owe an
element drop at an owning `T` that none of them performs.

**Alternatives measured in scratch and declined** (PD-2 records them):
`into[i] = move(from[i])` over the hoisted slices is `NITPICK-MOVE-001`; the
