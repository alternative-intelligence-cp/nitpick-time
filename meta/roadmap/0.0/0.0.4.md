# 0.0.4 — `src/core/` — DONE (2026-09-05)

> **Scope:** `Vec<T>`, `Bytes` and `limits.npk`. The storage primitives TM-005
> decided to own rather than import, plus the one file every named bound lives
> in.

## 1. Decisions taken at planning

- **P-23 — `Vec<T>`'s block is `wild`, its lifetime its owner's scope.** One
  `=>!` reinterpretation, in one file, checked once — the shape that survives.
  The compiler's 1.4.2 found five latent unchecked pointer reinterpretations in
  exactly the hand-written-per-family shape this replaces. **Every `Vec` has a
  `vec_free` and every scope that made one calls it**, or `exit 0` traps under
  D-151, which is exactly the enforcement wanted — **for the BLOCK. Read the
  note under §2's API table before relying on this sentence:** D-151 watches
  `wild` allocations, so it does not see an orphaned *element*, and P-23 is
  true only of the block (TM-106, `SAFETY.md` S-18b).
- **P-24 — `Bytes` is over `buffer`, not `wild`.** A `Bytes` is per-call
  scratch for a formatter, so the managed regime's scope-exit drop is right and
  there is nothing to pair. This differs from `Vec<T>` deliberately, and the
  difference is that one is a container the caller keeps and the other is a
  builder the caller consumes.
- **P-25 — `put_uint` is allocation-free**, writing decimal digits backwards
  into a stack array and appending. Every format emits numbers, and
  `int_to_string` allocates a `string` per call — the shape the compiler
  measured as quadratic in `npkg`'s first full run, seventeen minutes of
  fifty-six spent in the kernel.
- **P-26 — `put_int` is written and tested against `int64` MIN first.**
  Negating the most negative value overflows, and D-210 makes that a trap
  rather than a wrap — so the naive `if (v < 0) { v = -v; }` is a *crash* on
  one input. The implementation accumulates in the negative direction instead.
  This is the single most likely defect in this subcycle and it has one test
  before it has an implementation.
- **P-27 — `ntime` declares no map.** The zone lookup is a binary search over a
  sorted index (`ZONE_MODEL.md` Z-9), which at 447 entries beats a hash and has
  one invariant instead of four. If something later wants a map, that is a
  decision with a measurement behind it.

## 2. `Vec<T>`

```nitpick
pub struct:Vec<T> = { wild T->:items; int64:count; int64:cap; };
```

| Function | Contract (written as a comment now, `VERIFICATION.md` P-1) | element drop at an owning `T` |
|---|---|---|
| `vec_init<T>(cap)` | `ensures answer.count == 0 && answer.cap >= 1` | — |
| `vec_reserve<T>(v, need)` | `ensures v.cap >= v.count + need` | **blocked** (copies elements) |
| `vec_push<T>(v, move T:x)` | `ensures v.count == old(v.count) + 1` | — *(exempt: writes past the last live element)* |
| `vec_pop<T>(v)` | `requires v.count > 0` | **blocked** |
| `vec_at<T>(v, i)` | `requires i >= 0 && i < v.count` | — *(scalar `T` only; a copy is refused at an owning `T`, TYPE-046)* |
| `vec_set<T>(v, i, move T:x)` | `requires i >= 0 && i < v.count` | **blocked** |
| `vec_truncate<T>(v, n)` | `ensures v.count == min(n, old(v.count))` | **blocked** |
| `vec_clear<T>(v)` | `ensures v.count == 0` | **blocked** |
| `vec_free<T>(v)` | `ensures v.cap == 0 && v.count == 0` | **blocked** |

> **THREE CORRECTIONS TO THE TABLE ABOVE, MADE AT 0.0.4 AS THE ROWS WERE
> WRITTEN.**
>
> 1. **`result` → `answer`.** `result` is a reserved `VerificationKeyword`
>    (TM-130, `BUILD.md` B-18), so the contract as originally written could not
>    be compiled even as the comment it is today.
> 2. **`vec_free`'s `ensures v.items == NULL` → `ensures v.count == 0`.** The
>    implementation does not null the pointer, and `cap == 0` is the ownership
>    bit that matters. A contract claiming more than the code does is the defect
>    this repository amends specifications over, so it is amended here rather
>    than aspired to.
> 3. **The third column is new, and it is TM-132.** The subcycle was dispatched
>    believing O-N17 blocked ONE row (`vec_pop<T>`). It blocks **five**, because
>    all five are built on one primitive — `T:x = move(v.items[i])` in a generic
>    function at an owning `T` — and a loop is a different caller, not a
>    different primitive. Measured with a non-owning control built from the same
>    source for every case: `tests/probe/defect/generic_element_move/`, `case5`.
>
> **What ships (TM-132): `Vec<T>` AT A NON-OWNING `T`, stated in the file's own
> header and not merely here.** All nine rows are correct and tested at a
> non-owning `T`, which is every use `ntime` has. The element-drop path at an
> owning `T` is recorded as blocked, and `SAFETY.md` S-18b already puts element
> lifetime at the instantiation — where the two sanctioned concrete spellings
> are committed and measured.

> **Three of those entries discard elements and none of their postconditions
> says so** — `vec_free`, `vec_clear` and `vec_truncate` speak only of `count`,
> `cap` and `items`. At an **owning** `T` that is a leak, and **`exit 0` does
> not catch it**: D-151 watches `wild` allocations and a `string`'s body is
> managed. Cycle 0.0.0's probe 06 measured 125 MiB retained over 2 000 000
> elements at exit 0, and `HeapOom` under a 64 MiB cap. **TM-106** and
> `SAFETY.md` **S-18b** are the rule; this subcycle is where it is built, so
> each of the three needs an element-drop path for an owning `T` or a stated
> restriction to non-owning ones — and P-23's "or `exit 0` traps under D-151"
> must be read as being about the block alone.
>
> The shape is committed as `free_names` in `tests/probe/probe06_generic_vec.npk`.

**Rule:** `vec_at` returns by value and is therefore for scalar `T` only — for
an owning `T` a copy is refused (TYPE-046), and such a family reads through
`v.items[i]` at the site that knows the element's shape. This is the compiler's
own `List<T>` note and the reason there is no generic `list_at` there either.

## 3. `Bytes`

```nitpick
pub struct:Bytes = { buffer:body; int64:len; };
```

`init`, `reserve`, `push`, `extend`, `extend_str`, `put_uint`, `put_int`,
`len`, `view` (a borrowed `uint8[]`), `take` (an owned `string`), `clear`.
Growth doubles.

> **`free` WAS IN THIS LIST AND IS REMOVED (TM-133).** `Bytes`' body is a
> `buffer`, and `TYPE_REFERENCE.md` §23 lists `buffer_free` among the things
> **deliberately not landed** — *"the managed drop IS the free"*. So a
> `bytes_free` could only be a no-op, and a no-op named `free` would teach a
> caller to pair something that needs no pairing, in a repository where
> `vec_free` is genuinely mandatory. Its absence is P-24 working, not an
> omission. The reclaim was **measured** rather than assumed: 256 MiB of
> allocate-copy-overwrite churn peaks at 1 660 KiB.
>
> `reserve` is added, because `extend` and the two decimal writers need one
> reservation for a whole run rather than one per byte.

## 3. The finding that changed the subcycle: O-N17 blocks FIVE rows, not one

The dispatch ratified the defect as blocking **one row** of §2's nine-row
table, on the argument that *"the defect blocks one row of one table, not a
layer of the library"*. **That conclusion survives. Its premise did not.**

The primitive is not "popping". It is `T:x = move(v.items[i])` inside a generic
function at an owning `T`, and **five rows are built on it** — `vec_pop`,
`vec_set`, `vec_clear`, `vec_truncate`, `vec_free`. A loop is a different
caller, not a different primitive.

**Measured, every owning case with a non-owning control built from the SAME
source text:**

| shape | `T` | `npkc` | `llc` | link + run |
|---|---|---|---|---|
| move out and return (`pop`) | `string` | 0, `.ll` | **1, NO OBJECT** | — |
| move out and overwrite (`set`) | `string` | 0, `.ll` | **1, NO OBJECT** | — |
| move out and drop in a loop (`clear`) | `string` | 0, `.ll` | **1, NO OBJECT** | — |
| move out and drop, countdown (`truncate`) | `string` | 0, `.ll` | **1, NO OBJECT** | — |
| **all four, same source** | **`int64`** | **0** | **0, object** | **0, exit 0** |

Committed as `case5_generic_drop_loop.npk`. **TM-132** settles what ships:
`Vec<T>` at a **non-owning `T`**, stated in the file's own header, which is
every use `ntime` has.

**Why this is not the workaround W-11 forbids.** No function is bent around the
bug — each is the one that would have been written anyway — and §2 already
required *"an element-drop path for an owning `T` **or a stated restriction to
non-owning ones**"*, written before the defect was known. The defect removed
the first option; it did not invent the second. **What would have been a
workaround** is a generic `vec_clear<T>` that quietly does not drop: it would
leak at an owning `T`, pass `exit 0` because D-151 cannot see a managed body,
and read later as a design choice nobody would question.

**Had the one-row reading been accepted, that is exactly what would have
shipped.** `vec_clear` was on the "safe" side of it.

## 6. Deviations from the plan, each deliberate

- **`NTIME_OFFSET_MIN` added** (§4's table listed only the MAX; Z-19 states a
  two-sided range and every other bound here is a pair).
- **`NTIME_DIGITS_MAX` added** (`put_uint`'s buffer needs a size, and finding 1
  means the array cannot report its own).
- **`bytes_free` NOT written** — TM-133; `buffer` has no manual reclaim and a
  no-op named `free` would teach a caller to pair what needs no pairing.
- **`bytes_reserve` added**, so `extend` and the decimal writers reserve once
  per run rather than once per byte.
- **`vec_free`'s contract corrected** from `ensures v.items == NULL` to
  `ensures v.cap == 0 && v.count == 0`, because the body does not null the
  pointer and a contract claiming more than the code does is the thing this
  repository amends specifications over.
- **`result` → `answer`** throughout the contracts (TM-130).
- **`tools/ir_alloc_scan.py` added** so the "verified by reading the emitted IR"
  acceptance item is a command with an exit status. **Deliberately not a harness
  check yet**: a check belongs in `checks.py` with a planted-violation case in
  `selfcheck.py` proving it can fail, and inventing one at the end of a subcycle
  is how an instrument arrives untested on the day it is needed.
